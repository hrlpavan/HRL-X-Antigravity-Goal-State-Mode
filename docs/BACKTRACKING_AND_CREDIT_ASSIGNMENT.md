# Bounded Credit Assignment & Backtracking Protocol

In classical reinforcement learning, **credit assignment** refers to determining which actions are responsible for observed rewards or failures over long trajectories.

In LLM-based autonomous coding, bad credit assignment results in **infinite local thrashing**: an agent encounters an error caused by a flawed high-level architectural decision, but fruitlessly spends hours tweaking variable names, adding try/catch blocks, or making haphazard patches in a tight loop.

---

## 1. The Thrashing Trap vs. Bounded Backtracking

```
TRADITIONAL AGENT (Unbounded Thrashing):
[Flawed Strategy] ──► [Fail 1] ──► [Patch 1] ──► [Fail 2] ──► [Patch 2] ──► ... ──► [Context Blowout & Token Exhaustion]

FEUDAL HRL AGENT (Bounded Credit Assignment):
[Option Strategy] ──► [Fail 1] ──► [Patch 1] ──► [Fail 2] ──► [Patch 2] ──► [Fail 3]
                                                                                │ (Budget Exhausted!)
                                                                                ▼
[Meta-Replanning] ◄── [Revert Branch State: git checkout --] ◄───────────────────┘
```

---

## 2. The 3-Attempt Retry Budget Rule

Every subgoal option $\omega$ possesses an integer retry budget:
$$B(\omega) = 3$$

When an option fails its local validation check:
1. **Attempts $k \in \{1, 2\}$**: Local worker policy $\pi_\omega$ is granted permission to self-repair (e.g., fixing import errors, patching syntax typos).
2. **Attempt $k = 3$**: The local retry budget is strictly exhausted.

### Why exactly 3 attempts?
- Attempt 1: Catches minor syntax or import oversight.
- Attempt 2: Catches basic type mismatch or missed argument.
- If it still fails on Attempt 3, the underlying premise or architectural choice of the option is fundamentally flawed. Continuing to patch only corrupts the codebase.

---

## 3. The 3-Step Backtracking Procedure

When $k = 3$ is reached without passing verification, the Meta-Controller executes the following atomic sequence:

### Step 1: Branch Rollback
Revert all uncommitted or staged changes generated by the failing option:
```bash
git checkout -- .
git clean -fd
```
This guarantees that faulty experiments do not leave "debris" in the workspace that corrupt subsequent attempts.

### Step 2: Negative Credit Assignment to Option Policy
The failure is logged in the Meta-Controller's memory:
```json
{
  "failed_option": "g_2_jwt_cookie_auth",
  "strategy_attempted": "HTTP-only cookie with same-site strict",
  "failure_reason": "CORS preflight rejection across cross-domain reverse proxy",
  "assigned_credit": -1.0
}
```

### Step 3: Meta-Replanning (DAG Reformulation)
The Meta-Controller bypasses the failed option branch and synthesizes an alternative path in the task DAG:
```
Old Branch: g_2a (Cookie Auth) [FAILED & REVERTED]
New Branch: g_2b (Authorization Bearer Header with Refresh Token Handshake) [DISPATCHED]
```

---

## 4. Verification Check Before Replanning

Before the new option begins execution, the Meta-Controller confirms that the working directory has returned to a known good state:
```bash
test -z "$(git status --porcelain)"
```
Only when the slate is clean does the next worker option initiate.
